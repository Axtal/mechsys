1. CODE: lib/dem/domain.h

A. Domain::Save (around line 1740)

Comments only; no data-format change.  `xb` and `wb` were already written to
the HDF5 checkpoint.  The comment now states the contract explicitly:

    Persist both Verlet references.  Load restores them verbatim and does
    not call InitializeVelocity(), so a continuation starts from the same
    integrator history as the run that wrote the file.

B. Domain::Load (around line 2532)

Comments only; no functional change.  The comment records two facts:

- A loaded domain is already initialised.  Load preserves the saved `xb` and
  `wb`; it does not reinitialize the particles.
- Particles added AFTER a load are therefore NOT initialized by the next
  Solve().  The caller must call InitializeVelocity(dt) after adding or
  repositioning one.
- `FreePar`, `NoFreePar` and `Particle::Index` are derived state.  Solve()
  clears and rebuilds them after Initialize(), so Load intentionally leaves
  them alone.  Code that inspects or extends a loaded domain before the first
  Solve() must rebuild that partition itself.

An earlier version rebuilt FreePar/NoFreePar/Index inside Load.  That was
redundant for Load()-then-Solve() and has been reverted.

4. OUTSIDE MECHSYS (not a MechSys library change)
--------------------------------------------------

The large-pile continuation also required a fix in
/home/sergio/avalanche_dem/src/ricepile.cpp, not in MechSys:

    dom.Xmin = -cfg.exit_margin;
    dom.Xmax =  cfg.cell_Lx + cfg.exit_margin;

The previous restore code used +/-0.5*cell_Lx, which clipped the discharge
side of the base (the base spans x=0..cell_Lx) and eventually caused a
spurious base/box overlap.  The avalanche driver also rebuilds its own
free/fixed partition in RestorePile() before the first Solve(); it does not
depend on Load() doing so.

A Python renderer was also added at
/home/sergio/avalanche_dem/analysis/render_frames_3d.py for GIF rendering from
the driver's frames CSV.  It is not part of MechSys.
